# VMM audit — 2026-08-29

Scope: `src/qemu/` excluding the isolate files, plus `src/common/` and `src/abi/`.
Threat model: the guest is hostile and controls every byte it sends.

**Verdict: 13 findings — 0 critical, 6 serious, 7 minor.**

(Re-run after the audit was re-weighted toward races, ownership and signedness.
The second pass found one serious issue the first missed and quantified another,
which is the argument for the re-weighting.)

Explicitly checked and NOT found: any path where a guest value becomes a host
pointer. Every shm dereference goes through `slot_blob()` (`virtio_nvgpu.c:242`),
correctly applied at all six live call sites. The two places a guest value
becomes a host *descriptor* are findings 1 and 3 below, and both are lifetime
bugs rather than pointer forgery.

## Serious

**1. The guest chooses `h->size`, and every S-1 bound is expressed against it.**
`nvkvm_handle.c:206-243` (ftruncate at :214)
`NVKVM_REQ_OPEN_MEMORY_HANDLE` passes `req->size` to `ftruncate()` uncapped. Two
consequences: the guest mints arbitrarily large memfds and drives host page
commit through `MMAP_ON_ISOLATE`; and because the bound checks read
`req->offset > h->size || req->size > h->size - req->offset`, a `h->size` of 2^62
makes **every downstream bounds check vacuous**. The S-1 comment
(`nvkvm_handle.h:31-41`) treats `h->size` as a trustworthy extent without noticing
the guest picked it.

**2. `nvkvm_handle_attach_fd()` never checks the fd is the device it is labelled.**
`nvkvm_handle.c:173-191`; allocation at `nvkvm_isolate_handlers.c:745-767`
QEMU allocates a pending handle with the **guest's** `dev_id`, asks the isolate to
open it, and installs the returned SCM_RIGHTS fd with no `fstat`/`st_rdev`/type
validation. A compromised stub substitutes any fd it holds while QEMU goes on
labelling it `NVKVM_DEV_CTL` / `_GPU(n)` / `_DRM_RD(n)`. That fd is then dup'd
into other isolates via `COPY_HANDLE_TO_ISOLATE` and written as an embedded fd
into UVM ioctl params **QEMU itself issues** — so QEMU's own device-type gates
reason about `h->dev_id` while operating on something else entirely.
R2-M1 (`nvkvm_isolate.c:947`) hardens only against an fd arriving on the *wrong
response type*; nothing checks the identity of an fd on the right one.
Type confusion across the isolate boundary. NEW in the second pass.

**3. Present staging buffers freed by one thread while another dereferences them.**
`nvkvm_present_egl.c:902-955` (writer) vs `:1375-1405`, `:1540-1600` (readers)
`nvkvm_present_publish()` reads `have/idx/w/h` under `p->lock`, releases it, then
dereferences `p->stage[idx]` and memcpy's `w*h*4`. The present thread frees and
reallocates exactly those buffers whenever PRESENT geometry changes — which the
guest controls. The relay branch is worse: it reads `stage_buf[idx].memfd/.dmabuf`
entirely outside the lock, so after `nvkvm_udmabuf_free()` it can `dup()` a
**recycled fd number** — an unrelated QEMU fd — and pass it to the broker over
SCM_RIGHTS. RACE.

Second pass quantified the read: a stale `(w,h)` paired with a smaller new buffer
reads **up to ~268 MB of QEMU heap** into a surface the host *displays* and that
`screendump` can capture — so this is host memory disclosure, not only a UAF.

**4. `nvkvm_handle_get()` drops the table lock before returning the slot.**
`nvkvm_handle.c:245-258`; header claims otherwise at `nvkvm_handle.h:83`
The embedded-fd fixup (`nvkvm_isolate_handlers.c:2573-2581`) writes `hh->fd` as a
raw fd number into a parameter blob bound for the host UVM driver, on a thread-pool
worker, while a concurrent `CLOSE_HANDLE` on the TX thread closes and recycles it.
The C-2 fix (`nvkvm_handle_acquire_fd`) was applied to the *target* fd one line
below but not to the embedded ones. The stale header comment is what makes the
remaining call sites look safe. RACE.

**5. Broker reconnect un-latches `p->mode`, so both present paths can run at once.**
`nvkvm_present_egl.c:1700-1706` vs `:669-676` and `:684-783`
After readback mode has run the present thread owns the EGL context forever;
resetting `mode` lets the main loop pick the GL path and delete every cache entry
— with no current GL context — while the present thread is still reading them.
The comment at `:1131` states the invariant ("never both in one run, since the
mode is decided once") that `:1702` breaks. RACE.

**6. `virtio_nvgpu_device_unrealize()` never calls `nvkvm_sparse_fini()`.**
`virtio_nvgpu.c:1497-1526`; quarantine at `nvkvm_mmap_host.c:735-825`
`nvkvm_gpa_quar_purge()` is the only thing that removes a device's entries from
the process-wide quarantine and is called only from `sparse_fini()`. Entries
survive holding a stale `VirtIONvgpu *`, and a later drain dereferences
`nv->sparse_vmm_va`. Ownership disagreement: the quarantine assumes the device
outlives its entries; unrealize assumes nothing holds a reference.

## Minor (10)

BAR base below the shm block passes validation and shadows other MMIO
(`nvkvm_mmap_host.c:566`); wrapping page round-up in the sparse allocator
(`:644`, `:889`); `nvkvm_tables.c` using table index as KVM memslot number
(dead code, but a landmine); unenforced per-thread invariants in
`virtio_nvgpu.c:124,787,842`; find-or-create session race (`:91-109`);
used-ring length reported as `sizeof(out)` regardless of bytes written
(`:875` and 8 more); unthrottled `error_report()` per malformed request
(`:857`, `:1107`); non-atomic present statistics shared across threads
(`nvkvm_present_egl.c:1089-1122`); `console_fini()` abandoning cached EGLImages
and racing `forget_isolate()` (`:1639-1669`); a guest-controlled 32-bit index
reaching an `NV_ESC_RM_CONTROL` that QEMU issues in its own privileged process
(`nvkvm_isolate_handlers.c:3499` — bounded, host driver validates it).


## Checked and found SOUND — do not re-audit these

The second pass recorded what it verified as correct, which is as useful as the
findings:

- `slot_blob()`'s C-1 bound (`virtio_nvgpu.c:242-253`) covers every live shm
  consumer.
- The P2-2 double-fetch snapshot in `nvkvm_ioctl_work_fn` is correct.
- `nvkvm_present_geom_ok()` genuinely gates all three present paths, so the
  8192-dimension / pitch / `buf_size` bounds hold.
- `nvkvm_ring.h` peek/reserve bounds hold against a forged `head`/`tail`/`size`.
- `relay_clip_recv()` chunk accumulation is correctly bounded against
  `NVKVM_BROKER_CLIP_MAX_BYTES`.
- The A-21 KVM slot-pool gates are present and fail closed.
- `session->isolate_ids[]` and `client_allow[]` are bounds-checked at their
  write sites.

## Dead code, so its bugs are not reachable

The legacy `alloc_gpa` / `nvkvm_mmap_create` / `nvkvm_mmap_map_to_guest` bump
allocator in `nvkvm_mmap_host.c` and the whole of `nvkvm_objects.c` are reachable
only from an `#if 0` block — their missing free-list and unbounded
`collect_free_list` recursion do not matter today. `nvkvm_tables.c` is compiled
in but has no callers outside its unit test.
