# Isolate audit — 2026-08-29

Scope: `src/qemu/nvkvm_isolate*.{c,h}`, `nvkvm_ctrl_allowlist.h`, `src/stub/`.
Threat model: the guest is hostile, AND a compromised isolate must not reach the
host, another isolate, or another VM.

**Verdict: 23 findings — 5 critical, 12 serious, 6 minor.**

> **CORRECTION 2026-08-29:** two of the five criticals were over-rated on
> reachability. Guest *userspace* cannot compose `KILL_ISOLATE` or
> `CLOSE_HANDLE_ON_ISOLATE` — the guest module builds both from the fd's own
> context — and cross-VM is cross-process, so the blast radius is one VM's own
> isolates. Re-rated to low. The ring `_IOC_SIZE` smash is unaffected and stays
> critical: userspace picks the ioctl `cmd` that carries `_IOC_SIZE` into the
> ring. See `README.md` for the full correction.

**The headline is not any single bug: several of these mean the cross-isolate
boundary is not currently a boundary.** Four separate handlers take an
`isolate_id` straight off the wire and act on it with no ownership check.

## Critical

**1. Guest-chosen `_IOC_SIZE` into a 256-byte stack buffer — stack smash.**
`src/stub/nvkvm_stub.c:3013` (buffer `:2938`, filter `:2896`; the clamp that
exists only on the socket path is `:2396-2401`)
`ring_ctrl_must_punt()` constrains only bits 0-15 of `cmd`, leaving 16-29 free,
and the ring memfd is mapped into **guest physical memory**, so the guest authors
`rq.cmd` directly. The NVIDIA frontend then copies `_IOC_SIZE(cmd)` bytes — up to
16383 — in and back out of a 256-byte stack array. The file's own G-8 comment
(`:2385`) states the driver reads `_IOC_SIZE` regardless of `param_size` and
widens the allocation for it **on the worker path only**. Contradicts `:2818`'s
claim that "a malformed ring is fatal to THIS isolate only (DoS, never OOB)".

**2. Reader unlinks a pending entry, then bails without waking it.**
`nvkvm_isolate.c:1027` (unlink), `:1050`/`:1065` (`goto reader_exit`),
`:1180-1188` (wake loop), `:3479` (untimed wait)
`*pp = p->next` detaches the entry; both `goto reader_exit` paths — reached
whenever the stub announces a size then stalls past the 5 s `SO_RCVTIMEO` — leave
it woken by nobody. The pool worker blocks **forever** holding its
`VirtQueueElement`. Repeating it exhausts QEMU's shared 64-thread aio pool and
**wedges block I/O VM-wide**. The liveness argument at `:3471` rests entirely on
"the reader wakes every pending caller with -ECONNRESET", which is the guarantee
this breaks.

**3. `CLOSE_HANDLE_ON_ISOLATE` has neither ownership check its siblings have.**
`nvkvm_isolate_handlers.c:1005-1017`; stub `nvkvm_stub.c:2350`; unref
`nvkvm_isolate.c:3367`
Handle and isolate ids are one VM-global sequential space. Naming a neighbour's
`isolate_id` runs `nvkvm_iso_mmap_reap_handle()`, restoring anonymous backing
over the victim's **live device mappings while it is still writing through them**.
And because the stub's `handle_close_fd()` calls `send_ok()` unconditionally,
QEMU always sees `ret == 0` and always unrefs — so repeated calls naming a
foreign `handle_id` walk `isolate_refcount` to 0 and defeat the `-EBUSY` guard.

**4. `KILL_ISOLATE` destroys any isolate in the VM on a bare 12-bit id.**
`nvkvm_isolate_handlers.c:858-862`
`{isolate_id, reserved}` — no token, no session, no ownership check of any kind.
Then reaps the victim's mappings, forgets its window, destroys its session and
force-closes every host fd it owned. Strictly worse than the documented munmap
gap: it needs no `mmap_token`, and the id space is 4096 slot indices.

**5. Sparse-GPA extent leaked on three error paths.**
`nvkvm_isolate_handlers.c:4024`, `:4053`, `:4207`
`nvkvm_sparse_gpa_alloc()` transfers ownership; the `!target` return, the
`qva == MAP_FAILED` return and the stub-mirror rollback do not free it, and the
extent is never recorded in `iso_mmap_tbl` — so **no reclaim path, including
isolate death, can ever find it**. `TYPE_NVIDIA` handles skip the S-1 extent
check, so a bogus offset makes the `mmap()` fail deterministically after the
allocation. One request with `length == sparse_size` permanently consumes the
whole 128 GiB window.

## Serious (12) — the theme

**The boundary is porous by construction, and the tokens meant to protect it are
not secrets.** `mmap_token` is a bare round-robin index into a VM-global
8192-entry array with no randomness and no generation
(`nvkvm_isolate_handlers.c:518-541`) — so the documented cross-isolate munmap gap,
whose comment implies the token is a secret, is **enumerable in 8191 requests**,
and `iso_mmap_free` reports "not yours" and "not there" identically.

Compounding it: on the **default** configuration the preferred rung is
`NS|SECCOMP` with **no `LAYER_UID`**, so every isolate runs as QEMU's own uid,
separated only by namespaces and a 20-syscall filter
(`nvkvm_isolate_uid.h:846`). A degraded rung — including seccomp-only, whose own
report string says "Isolates are NOT separated from each other" — is warned about
at realize and **never refused** (`virtio_nvgpu.c:1331`).

Also serious: the C-2 raw-fd hazard applied to two of three sites, leaving the
UVM embedded-fd path reading `hh->fd` after the lock is dropped (`:2572`);
embedded RM-ctrl-fd handles looked up with no type/device/session check while the
sibling REALIZE path validates the identical field three ways (`:2572` vs
`:4866`); the P2-2 double-fetch snapshot applied to the IOCTL worker only, so
REALIZE validates guest-writable shared memory in place and then ships those same
pages (`:4849`); `map_flags` forwarded unmasked into the privileged stub's
`mmap()` while `prot` is masked and the sibling path masks both (`:3994`);
`nvkvm_handle_close_session()` ignoring the `isolate_refcount` guard that
`nvkvm_handle_close()` enforces; an isolate that dies **without** a guest
`KILL_ISOLATE` never having its slot, child, uid or mapping records reclaimed —
`in_use` is cleared in exactly one function (`nvkvm_isolate.c:2322`); an
unconditional ALLOW for any control command with bit 15 set, ahead of the
default-deny table (`nvkvm_ctrl_allowlist.h:313`); the stub's reported `host_va`
trusted verbatim despite the protocol header asserting every response value is
range-checked; `CLOSE_HANDLE` purging UVM VA-ownership records before the close
that legitimately returns `-EBUSY`, bricking another session's UVM context; and
every synchronous isolate command holding **QEMU's BQL across a 30-second round
trip**, so an unresponsive stub freezes the main loop, QMP, timers and all vCPUs.

## Minor (6)

`POLL`/`UNPOLL_ON_ISOLATE` with no validation of either id half — and the note
that these are two of **eight** `isolate_id`-taking handlers with no ownership
check, where the munmap comment claims "three of the five"; `GET_PID_INFO`
resolving any isolate id to its host tgid (host PIDs are the prerequisite for
signal/ptrace on rungs with no PID namespace); `REALIZE_UVM_MAPPING` reporting
success on `ret == 0, host_va == 0`; `OPEN_NVIDIA_HANDLE` evaluating its graphics
gate on a **signed** cast of a guest `__le32`, so bit 31 skips the gate the
comment calls authoritative; the NVKMS vblank quota released on an unrelated size
field; and the isolate window VA reaching the guest through
`NVOS33.pLinearAddress`, defeating the ASLR the window design requires — which,
combined with finding 1, turns a blind stack overflow into a targeted one.
