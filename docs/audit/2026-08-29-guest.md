# Guest kernel module audit — 2026-08-29

Scope: all of `src/guest/` plus `src/common/` wire protocol. Read-only audit.
Threat model: unprivileged guest userspace below the module is hostile, and the
host/VMM reply is untrusted input.

**Verdict: 12 findings — 1 critical, 8 serious, 3 minor.**

Ownership, lifetime and locking dominate; only two findings are plain missing
bounds checks. That is the expected shape and the reason the audit was weighted
that way.

Verified as NOT a finding: the first-open NULL-deref gate. `nvkvm_transport_ready()`
gates `nvkvm_fd_ctx_open_dev()` (`nvkvm_main.c:775`), the sole entry for both
`nvkvm_open()` and `nvkvm_drm_open()`; no path misses it.

---

## Critical

**1. Borrowed `fd_ctx` used across a blocking round-trip after its reference was
dropped — UAF.**
`nvkvm_drm.c:327` (put at :346, :377; consumed at :799-813, :899-913)

`nvkvm_gem_resolve_fwd()` calls `drm_gem_object_put(obj)` and *then* returns
`ng->ctx`. That GEM reference is the only thing keeping the ctx alive
(`nvkvm_gem_proxy_create`, :232; released in `nvkvm_gem_free()`). A concurrent
`GEM_CLOSE` of the last handle frees the ctx while the first thread is inside
`nvkvm_virtio_ioctl_on_isolate(ctx, …)` reading `ctx->session->isolate_id`.

The correct pattern is 30 lines away: `nvkvm_fb_stub_handle()` (:380) is safe only
because the KMS present path holds a framebuffer reference for the whole call
(`nvkvm_kms.c:544-550`). **The two sites disagree about whether the returned ctx
is owned or borrowed** — exactly the ownership-confusion class.

Reachable by unprivileged guest userspace. RACE.

## Serious

**2. AB-BA deadlock between `ext_lock` and `mmap_lock`.**
`nvkvm_main.c:2770` vs `nvkvm_mmap.c:398` (read side `nvkvm_virtio.c:1424`)
UVM ioctl path takes `ext_lock` then `mmap_read_lock`; the UVM mmap path is
entered holding `mmap_write_lock` and then takes `ext_lock`. Both waits are
uninterruptible, so the process becomes unkillable with `mmap_write_lock` held —
every reader of its `/proc/<pid>/maps` hangs too. The existing `_nomm` comment
(`nvkvm_virtio.c:1533`) considers only the mmap→ioctl direction.

**3. Unbounded guest-kernel memory leak on every fail-closed `-EBADF`.**
`nvkvm_main.c:2139, :2187, :2233`; also `nvkvm_drm.c:830, :906`
The early return skips `kfree(aux_buf); kfree(params_buf)` at :3186 that every
other error exit performs. A loop leaks up to 64 KiB per iteration until OOM.
`nvkvm_drm.c:830` additionally leaves an internal stub handle in `p->handle`,
which `drm_ioctl()` copies back to userspace.

**4. `struct nvkvm_inflight` used uninitialised on both munmap-unwind paths.**
`nvkvm_mmap.c:258, :1320`
Only `.done` and `.txn_id` are set; `nvkvm_send_sync()` branches on
`inf->isolate_id` and may `nvkvm_virtio_interrupt_isolate()` an arbitrary isolate
from stack garbage. `nvkvm_mmap_release_fd()` runs at process exit where SIGKILL
is pending by construction, so the interruptible branch is the common case. Both
sites also mint `txn_id` directly, bypassing the collision-avoiding allocator.

**5. A documented "no caller holds mmap_lock" invariant that is already false.**
`nvkvm_mmap.c:709-716` (comment) vs path `nvkvm_mmap.c:157 → nvkvm_uvm_ext.c:427
→ :409 → nvkvm_main.c:838 → nvkvm_mmap.c:1262`
`nvkvm_vma_close()` runs from `remove_vma()` under `mmap_write_lock` and reaches
`nvkvm_cpu_page_unmap_guest()`, which takes `mmap_write_lock` on the same mm —
self-deadlock on a non-recursive rwsem. It does not fire today only because that
ctx never accumulates `cpu_pages`; nothing enforces it, and the comment
enumerating callers omits this one.

**6. Host-negotiated `slot_size` never validated against the mapped region.**
`nvkvm_virtio.c:795-802`, used at `:88`
Checked only as power-of-two ≥ 4096. `nvkvm_slot_addr()` computes
`shm_base + slot * slot_size` for slot ≤ 255, so a VMM advertising a 1 GiB
slot_size against a 16 MiB BAR turns every slot `memcpy` into a write to an
arbitrary kernel address. `shm_size` is recorded at `:898` and never consulted.

**7. `(__u64)p->limit + 1` overflows to 0, forwarding a raw guest VA to the host.**
`nvkvm_ioctl.c:436-452`
`limit = U64_MAX` passes the `> 0` guard, yields `len == 0`,
`nvkvm_cpu_pages_migrate_range()` returns early, and the `else` branch that zeroes
`p_memory` is skipped — defeating the invariant the sanitizer exists to enforce.

**8. Host-returned `nbytes` bounds-checked against a constant, not `slot_size`.**
`nvkvm_hostfile.c:74-75, :301-303`
`NVKVM_HFILE_MAX_SIZE` is 8192 while `slot_size` may legally be 4096, so
`seq_write()` over-reads 4 KiB of the adjacent slot — another process's ioctl
parameters — into `/proc/driver/nvidia/version`, which is mode 0444.

**9. `nvkvm_virtio_fini()` frees the virtqueues without draining `inflight_list`.**
`nvkvm_virtio.c:918-947`
Waiters in `wait_for_completion()` sleep forever on a queue that no longer exists;
`complete()` can only come from a TX callback that can no longer run. Device
hot-unplug or `rmmod` with a forwarded ioctl outstanding leaves unkillable tasks.

## Minor

**10.** `ctx->poll_armed` set before the arm request and never cleared on failure
(`nvkvm_main.c:3273-3280`) — one transient failure permanently pins the fd to the
~18 ms fallback. Also does a blocking virtio round-trip inside `->poll`, which
epoll calls holding `ep->mtx`.

**11.** `nvkvm_cpu_pages_migrate_range()` retypes whatever VMA covers the range to
`VM_PFNMAP|VM_IO` without checking it is anonymous private memory
(`nvkvm_mmap.c:1505-1520`). Blast radius is the caller's own address space, but
the surrounding comments' assumptions are never checked.

**12.** `nvkvm_evt_deliver()` matches on host-supplied `(isolate_id, handle_id)`
with no ownership check (`nvkvm_main.c:653-670`) — a malicious VMM can set poll
bits on any guest process's fd. Bounded to spurious wakeups.
